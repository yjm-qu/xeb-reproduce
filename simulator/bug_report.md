# uniqc 库 TwoQubitDepolarizing 噪声参数缓存 Bug 问题报告

## 1. 问题现象

在使用 uniqc 量子模拟器进行 XEB 实验时，我们发现了一个隐藏在库深处的 bug：**双比特门的去极化噪声参数 p 在同进程内无法动态修改**。

具体表现为：当我们在一个 Python 进程中对双比特门（如 ISWAP、CZ、CNOT、SWAP）连续施加不同的 depolarizing probability 时，后续所有调用的噪声强度都会被"钉死"在第一次调用时的 p 值上，无论传入什么新值都无效。

### 实验证据

在同一次 Python 进程内，对双比特门施加从 p=0.1 到 p=0.9 的不同噪声参数，测量实际错误率 ε：

| 设定 p | 实测 ε | 预期 ε |
|--------|--------|--------|
| 0.1 | 0.0790 | ~0.075 |
| 0.2 | 0.0793 | ~0.15 |
| 0.3 | 0.0820 | ~0.23 |
| 0.4 | 0.0776 | ~0.30 |
| 0.5 | 0.0791 | ~0.38 |
| 0.9 | 0.0808 | ~0.68 |

**现象**：p 从 0.1 增大到 0.9（9 倍），但 ε 始终徘徊在 0.08 左右，毫无变化。

作为对比，单比特门的 Depolarizing 通道完全正常：

| 设定 p | 实测 ε | 预期 ε |
|--------|--------|--------|
| 0.1 | 0.0648 | ~0.05 |
| 0.2 | 0.1277 | ~0.10 |
| 0.3 | 0.2060 | ~0.15 |
| 0.5 | 0.3253 | ~0.25 |
| 0.9 | 0.6023 | ~0.45 |

单比特门的 ε 随 p 线性增长，符合物理预期。

---

## 2. 问题触发条件

经过系统性的排查，我们确定了以下触发条件：

1. **同进程内连续调用**：必须在同一个 Python 进程内连续调用含 TwoQubitDepolarizing 的模拟
2. **使用 ErrorLoader_GateTypeError**：通过 `gatetype_error` 字典为双比特门指定噪声
3. **门类型**：ISWAP、CZ、CNOT、SWAP 等双比特门均受影响，单比特门不受影响
4. **与 p=0 无关**：早期认为"先跑 p=0 再跑 p>0"才会触发，后来发现**任何不同的 p 值连续调用都会互相影响**

### 验证过程

```python
# 同进程内连续调用不同 p 值
for p in [0.01, 0.008, 0.006]:
    em = ErrorLoader_GateTypeError(
        generic_error=[Depolarizing(p=0)],
        gatetype_error={'ISWAP': [TwoQubitDepolarizing(p=p)]}
    )
    sim = NoisySimulator(backend_type='statevector', error_loader=em)
    # ... 结果：所有 p 都返回类似的 epsilon（约 0.008）
```

---

## 3. 定位过程

### 3.1 排除法定位

我们首先排除了以下可能性：

- **不是 gatetype_error 字典本身的问题**：单比特门使用同样的字典结构工作正常
- **不是 Circuit 或 Simulator 的问题**：更换不同的 Circuit 构建方式结果相同
- **不是特定门的问题**：测试了 ISWAP、CZ、CNOT、SWAP，全部受影响
- **不是 p=0 特殊处理的问题**：直接跳到 p>0 仍然被钉死

### 3.2 进程隔离验证

将每次模拟放到独立子进程中执行，问题消失：

```python
# 子进程隔离方案（有效但极慢）
import subprocess
result = subprocess.run(
    ['python', '-c', f'simulate(p={p})'],
    capture_output=True
)
```

这证实了问题出在**进程级状态**，而非算法或逻辑错误。

### 3.3 时间线

- 首次发现：2026-08-16，在标定实验中观察到双门 ε-p 关系不符合预期
- 初步归因：以为是 p=0 先验导致的问题
- 深入验证：2026-08-22，扩大 p 的范围 [0.1, 0.9]，确认无论什么 p 值都会被钉死

---

## 4. 原因分析

### 4.1 现象层分析

从测试结果来看，TwoQubitDepolarizing 对象在第一次创建后，其内部状态被某种机制"固化"了。后续即使创建新的 TwoQubitDepolarizing(p=new_p) 对象并传入模拟器，实际生效的仍然是第一次的 p 值。

### 4.2 根因猜测

根据现象推断，最可能的原因是 **uniqc 库的 native 层（C++/pybind11）存在模块级缓存**：

1. **ErrorLoader 内部缓存**：ErrorLoader_GateTypeError 在 native 层维护了一个全局 dict 或缓存表，第二次创建时直接复用第一次的 noise 对象
2. **TwoQubitDepolarizing 对象复用**：TwoQubitDepolarizing.__init__ 在 native 层只解析一次 p 参数，后续忽略新传入的值
3. **NoisySimulator 缓存**：NoisySimulator.simulate_shots 内部用 weakref 缓存了第一次调用的 noise_model

### 4.3 为什么不影响 xeb_v2.py

有趣的是，我们的 XEB 实验代码（xeb_v2.py）没有受此 bug 影响。原因是 xeb_v2.py 在每次实验开始时就固定了噪声参数（EPS1=0.0028, EPS2=0.0071），不会在同进程内动态修改 p 值，因此不会触发缓存问题。

---

## 5. 解决方案与建议

### 5.1 临时规避

- **方案 A（推荐）**：避免在同进程内修改 p 值，标定实验使用子进程隔离
- **方案 B**：每次实验使用独立的 Python 进程（代价：极慢）
- **方案 C**：固定 p 值后不再修改（如 xeb_v2.py 的做法）

### 5.2 根本解决

需要 uniqc 库的维护者：
1. 检查 native 层是否存在模块级缓存
2. 验证 TwoQubitDepolarizing 对象是否被复用
3. 在修改 p 参数时强制重新初始化，而不是复用已有对象

---

## 6. 结论

本次问题揭示了 uniqc 库在双比特门噪声建模上的一个隐藏 bug。该 bug 具有很强的隐蔽性——只有在动态调整噪声参数时才会暴露，而大多数静态实验（如我们的 XEB 主实验）不会触发。

通过系统的排除法定位、进程隔离验证和扩大参数范围的补充实验，我们最终确认了问题范围和触发条件，并找到了可行的规避方案。这一过程也为后续使用 uniqc 库的其他研究者提供了参考。
